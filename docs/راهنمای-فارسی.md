# راهنمای فارسی — کنترل هارنس‌ها با Harness2

این راهنما برای کسی نوشته شده که می‌خواهد روی این ماشین چند ابزار عامل (harness)
را کنار هم مدیریت کند، همه را از یک دروازهٔ مدل عبور دهد، و هر کدام را مستقل نگه دارد.

---

## ۱. این چیز اصلاً چیست؟

سه چیز را جدا نگه دار:

| چیز | کارش |
|---|---|
| **هارنس** | ابزاری که با مدل کار می‌کند: pi، opencode، dsh، claude code، و T3 Code. هر کدام config و CLI خودش را دارد. |
| **9router** | دروازهٔ مدل روی `127.0.0.1:20128`. همهٔ هارنس‌ها مدل را از اینجا می‌گیرند. |
| **Harness2** | خودش مدل را صدا نمی‌زند. هارنس‌ها را می‌شناسد، config هر کدام را می‌خواند و می‌نویسد، و می‌تواند از طریق هر کدام یک تسک اجرا کند. |

**هارنس‌ها همتا هستند، نه تودرتو.** هیچ‌کدام زیر دیگری نیست. تنها چیزی که
شریک دارند 9router است.

**T3 Code (`t3code`) با بقیه فرق دارد.** خودش یک هارنس نیست، یک «سطح کنترل»
است — مثل خود Harness2. هارنس‌هایی را که روی PATH پیدا کند می‌چرخاند و وب/موبایل
اضافه می‌کند. سه نکته که با اجرا تأیید شده‌اند:

- در یک کانتینر جدا زندگی می‌کند: `/media/kourosh/DEVNVME/tools/t3code-001/`،
  ایمیج `192.168.1.13:7001/t3code:0.1.7`. تنها راه ورود `docker exec` است، چون
  خود CLI سروِر را از `<home>/userdata/server-runtime.json` پیدا می‌کند و
  `--url` ندارد. پوشش `~/.local/bin/t3` همین کار را می‌کند.
- `apply t3code` هیچ لیست مدلی نمی‌نویسد: T3 Code مدل‌ها را در دیتابیس خودش
  نگه می‌دارد، نه در یک فایل config. کاری که می‌کند نوشتن `service.env` است —
  همان تنها فایلی که T3 Code می‌خواند — تا پراوایدر claude آن به دروازه وصل شود.
- `can_run` روشن است: T3 Code هارنس‌ها را می‌چرخاند ولی خودش هیچ‌کدام را ندارد،
  پس `claude@2.1.318` داخل ایمیج نصب شده و از طریق همان متغیرهای `service.env`
  به دروازه وصل می‌شود. دو نکته که با اجرا پیدا شد: کانتینر نباید root باشد
  (claude با `--dangerously-skip-permissions` زیر root کار نمی‌کند، پس `user:
  "1000:1000"`)، و مدل باید `claude-sonnet-4-6` باشد چون دروازه فقط همین را
  بدون پیشوند جواب می‌دهد.

## ۲. دستورهای اصلی

همه از پوشهٔ `harness2` و با venv فعال:

```bash
cd /media/kourosh/DEVNVME/projects/harness2
source .venv/bin/activate
```

| دستور | کار |
|---|---|
| `harness2-web` | **پنل وب برای چند پروژهٔ هم‌زمان** |
| `harness2-harness list` | کدام هارنس‌ها نصب‌اند |
| `harness2-harness do "تسک"` | **خودش هارنس را انتخاب می‌کند و اجرا می‌کند** |
| `harness2-harness route "تسک"` | فقط نشان می‌دهد کدام هارنس انتخاب می‌شود و چرا |
| `harness2-harness show pi` | config فعلی pi و گروه مدلش |
| `harness2-harness models pi` | کدام مدل‌های دروازه برای pi مجازند |
| `harness2-harness apply pi` | گروه مدل را در config خودِ pi بنویس |
| `harness2-harness run pi "سلام"` | یک اجرای سریع headless |
| `harness2-harness bench pi "تسک" --run-id x/y --results-root /tmp/r` | اجرای یک تسک با ساختار کامل پوشهٔ نتیجه |
| `harness2-harness trace pi` | لاگ خودِ pi و خطوط دروازه |
| `harness2-harness keys` | کلیدهای دروازه |

## ۳.۲. پنل وب — چند پروژه هم‌زمان

اگر می‌خواهی چند پروژه را هم‌زمان به هارنس‌ها بسپاری و بین‌شان سوییچ کنی:

```bash
harness2-web                     # http://127.0.0.1:8090
```

یا از منوی اپلیکیشن‌ها **Harness2 Tasks** را بزن — خودش باز می‌شود.

در پنل:

- **تسک جدید**: کادر تسک + انتخاب پروژه + انتخاب هارنس (یا `auto` مثل `do`)
- **فهرست تسک‌ها**: همه با وضعیت، پروژه، هارنس و مدل
- **جزئیات**: لاگ زنده، فایل‌های تحویل‌شده، و اینکه چرا آن هارنس انتخاب شد

### ادامه دادن یک تسک

هر تسک معمولاً از صفر شروع می‌شود: فضای کار تازه، و هیچ خاطره‌ای از تسک
قبلی. روی یک تسک تمام‌شده دکمهٔ **Continue this task** این را برای یک
پیگیری عوض می‌کند: تسک جدید **در همان فضای کاری** اجرا می‌شود (پس
فایل‌های قبلی سر جایشان‌اند) و هارنس گفتگوی قبلی را ادامه می‌دهد. یعنی
«حالا مرحلهٔ ۲ را انجام بده» روی طرحی که همین الان نوشته، کار می‌کند.

پروژه و هارنس از تسک قبلی ارث می‌رسند. زدن **Continue this task** انتخابگر
پروژه و هارنس را هم روی همان مقادیر می‌برد — چیزی که واقعاً اجرا می‌شود
همان ارث‌رسیده است، و اگر انتخابگر روی مقدار قبلی می‌ماند، پیگیری طوری به
نظر می‌رسید که در پروژهٔ دیگری اجرا خواهد شد. این دکمه فقط برای هارنس‌هایی
است که `continue_flag` دارند — claude، pi و opencode دارند.

dsh هم می‌تواند ادامه بدهد، ولی نه با این دکمه: پروفایل headless آن
`--session-id <id>` می‌گیرد که **session موجود** را می‌پذیرد و روی id ناشناس
خطا می‌دهد. پس id را نمی‌شود از اول انتخاب کرد؛ باید از رویداد `session`
اجرای اول برداشت و به اجرای بعد داد. هنوز کسی این کار را نمی‌کند، پس dsh در
پنل فقط «شروع» است، نه «ادامه».

فهرست تسک‌ها در `runs/web/index.json` ذخیره می‌شود، پس ری‌استارت پنل آن را
از دست نمی‌دهد و امکان ادامه با آن می‌ماند. تسکی که وسط کار بوده، بعد از
ری‌استارت `interrupted` نشان داده می‌شود — پروسه‌ای که رفته نمی‌تواند هنوز
در حال اجرا باشد.

### نکتهٔ مهم: کجا اجرا می‌شود؟

هر تسک فضای کار جدا دارد:

| پروژه | کجا اجرا می‌شود |
|---|---|
| اگر git باشد | یک **clone موقت** — پروژهٔ اصلی دست‌نخورده می‌ماند |
| اگر git نباشد | مستقیم در خود پوشهٔ پروژه |

برای همین در فهرست پروژه‌ها، جلوی مخزن‌ها `·git` نوشته شده. اگر پروژه‌ای git
باشد، خیالت راحت است که هارنس نمی‌تواند فایل‌هایت را خراب کند — خروجی را در
clone می‌بینی و هر چه خواستی خودت برمی‌داری.

**دکمهٔ Cancel** پروسهٔ هارنس را واقعاً می‌کشد: اول SIGTERM (تا لاگش را تمیز
بنویسد) و اگر گوش نداد SIGKILL. تسکِ کنسل‌شده `failed` می‌ماند و حتی اگر فایلی
قبل از کشتن نوشته شده باشد، به `done` برنمی‌گردد.

**محدودیت:** پنل احراز هویت ندارد، پس روی لوپ‌بک می‌ماند مگر خودت بازش کنی.

## ۳.۵. دادن تسک به دست خودش

اگر نمی‌خواهی مشخص کنی کدام هارنس، `do` را بزن:

```bash
harness2-harness do "این باگ را در auth.py درست کن"
```

خودش هارنس را از روی متن تسک انتخاب می‌کند، اجرا می‌کند، و **اگر آن یکی
شکست خورد، بعدی را امتحان می‌کند**:

```
→ pi  (model All)
  ok — delivered ['answer.txt']
  run dir: runs/do/t1/pi
  routed by: matched bug
```

**تسک لازم نیست فایل بسازد.** اگر سؤال بپرسی، جواب خودش خروجی است:

```
→ claude-code  (model claude-sonnet-4-6)
  ok — answered (no file written)
  answer:
    DOCFIX-OK
```

فقط وقتی «همه شکست خوردند» می‌بینی که واقعاً خروج غیرصفر باشد یا هیچ جوابی
نیاید. یک جواب متنی موفق، شکست نیست.

فقط ببین کدام را انتخاب می‌کند، بدون اجرا:

```bash
harness2-harness route "ترجمهٔ این ۵۰۰ ایمیل"
```

### انتخاب چطور انجام می‌شود

در manifest هر هارنس دو چیز نوشته شده — کلمات مناسبش و رتبه‌اش:

```toml
routes = ["code", "debug", "bug", "refactor", "test"]
priority = 10
default = false
```

router هر هارنسِ **قابل‌اجرا** را می‌شمارد که چند کلمه از `routes` در تسک
آمده، تساوی را با `priority` می‌شکند، و برنده را برمی‌دارد. تسکی که به هیچ
کلمه‌ای نخورد به هارنسِ `default` می‌رود؛ اگر آن هم نبود، بالاترین priority.
یعنی router همیشه جواب می‌دهد و هیچ‌وقت رد نمی‌کند.

کلمات **فقط به‌صورت کلمهٔ کامل** تطبیق می‌شوند. اگر substring بود، `git` داخل
`digital` و `web` داخل `website` فعال می‌شد و لیست کلیدواژه‌ها بی‌اعتبار می‌شد.

برای رد کردن تصمیم: `--harness pi`. برای مدل مشخص: `--model All`.

### نکتهٔ هزینه

هر تلاش fallback یک اجرای کامل است. اگر 9router کند باشد گران تمام می‌شود.
وقتی یک فراخوانی قابل‌پیش‌بینی می‌خواهی، `--no-fallback` بزن.

### تنظیم کلمات

فقط `routes` را در manifest عوض کن:

```bash
nano harness2/harnesses/manifests/pi.toml
```

مثلاً اگر می‌خواهی pi کارهای داکر هم بگیرد: `"docker"` را اضافه کن.
`harness2-harness route "..."` را بزن تا اثرش را ببینی.

## ۴. مدل‌ها چطور جدا می‌مانند؟

هر هارنس یک **گروه مدل** دارد که در manifestش نوشته شده
(`harness2/harnesses/manifests/*.toml`). مثلاً pi فقط کامبوها را می‌بیند،
claude code فقط کلود، و dsh خانوادهٔ `*qwen*`/`*glm*`/`*deepseek*` به‌علاوهٔ
`claude-sonnet-4-6` و `ag/*` (چون روی این دروازه فقط دو مورد آخر جواب می‌دهند).

نکتهٔ الگوها: idهای دروازه **namespace دارند** (`bai/glm-5.3`،
`Yeta/deepseek-v4.1-flash`). پس الگوی خانواده باید `*glm*` باشد، نه `glm*`.
شکل دوم هیچ‌وقت تطبیق نمی‌خورد (چون id با `glm` شروع نمی‌شود) و گروه خالی
می‌ماند — که موقع اجرا شبیه خطای provider به‌نظر می‌رسد، نه خطای الگو.

`harness2-harness apply <harness>` این گروه را داخل config خودِ هارنس می‌نویسد.
مدلی که در گروه نباشد در config غایب است و هارنس ردش می‌کند:

```
$ harness2-harness apply pi
pi: 8 models -> /home/kourosh/.pi/agent/models.json
  backup /home/kourosh/.pi/agent/models.json.bak-20261025-072619

$ pi --print "hi" --model 9router/gemini-2.5-flash
Warning: Model "gemini-2.5-flash" not found for provider "9router"...
404: No active credentials for provider: gemini
```

**نکتهٔ مهم:** کلید هر هارنس در 9router یک allow-list دارد، ولی 9router نسخهٔ
0.5.109 آن را **اجرا نمی‌کند** (تست شد: کلیدی که فقط `All` را مجاز کرده بود،
مدل `Safe` را هم سرو کرد). پس جداسازی واقعی در **config خودِ هارنس** است، نه
در دروازه. allow-list فقط برای ثبت در داشبورد است.

## ۵. تغییر گروه مدل یک هارنس

manifest را باز کن و `allowed_models` را عوض کن:

```bash
nano harness2/harnesses/manifests/pi.toml
```

مقدارها glob هستند — یعنی الگو، نه لیست دقیق:

```toml
allowed_models = ["All", "Safe", "Coding", "local"]
# یا الگوی خانواده — توجه: `*qwen*` نه `qwen*` (idها namespace دارند):
allowed_models = ["*qwen*", "*glm*"]
# خالی بگذاری = بدون محدودیت:
allowed_models = []
```

بعد اعمال کن:

```bash
harness2-harness apply pi
```

بی‌خطر است: همیشه از فایل قبلی backup می‌گیرد و تنظیمات دیگرت را دست‌نخورده
می‌گذارد.

## ۶. دنبال‌گیری از 9router

`trace` دو چیز می‌دهد:

```bash
harness2-harness trace pi --limit 2 --tail 3
```

- **لاگ خودِ هارنس** (سشن‌های pi) — اینجاست که می‌فهمی کدام هارنس چه فرستاده.
- **خطوط دروازه** (از `docker logs router9`) — ولی این خطوط **نمی‌گویند کدام
  هارنس** درخواست را فرستاده. فقط `conn=` (اکانت upstream) را نشان می‌دهند.

یعنی برای انتساب، لاگ خودِ هارنس تنها نیمهٔ مفید است.

## ۷. باینری‌ها روی PATH

`claude` خودش روی PATH می‌آید. سه‌تای دیگر نه:

مخازن ابزار زیر `/media/kourosh/DEVNVME/tools/` هستند: `opencode`،
`deepseek_harness`، `pi_harness` و `t3code-001`. مخزن opencode با متغیر
`OPENCODE_DIR` قابل جابه‌جایی است (نگاه کنید به `harness2/config.py`)؛
چک‌اوت‌های بنچمارک و `opencode-config` هنوز زیر `dependencies/` می‌مانند.

```bash
# pi و dsh فایل اجرایی با shebang نود دارند، پس symlink کافی است:
ln -sf ~/tools/pi_harness/packages/coding-agent/dist/bundle/cli.js ~/.local/bin/pi
ln -sf ~/tools/deepseek_harness/apps/cli/lib/bin.js           ~/.local/bin/dsh
```

برای **opencode** یک wrapper لازم است، نه symlink — نسخهٔ pin شده باینری build
شده ندارد و `bin/opencode` داخل پکیج ESM، CommonJS است و با
`ReferenceError: require is not defined` می‌افتد. Harness2 از source با bun
اجرا می‌کند:

```bash
cat > ~/.local/bin/opencode <<'EOF'
#!/bin/bash
exec /path/to/harness2/dependencies/tools/node_modules/.bin/bun \
  run --cwd /path/to/tools/opencode/packages/opencode \
  --conditions=browser src/index.ts "$@"
EOF
chmod +x ~/.local/bin/opencode
```

امتحان:

```bash
pi --version && dsh --version && opencode --version
```

راه دیگر: در manifest مقدار `binary` را مسیر مطلق بده و PATH را کلاً دور بزن.

سه نکتهٔ دیگر که manifest مربوط به opencode رمزگذاری می‌کند؛ هر کدام یک
شکست واقعی بود:

- **شناسهٔ مدل باید پیشوند provider داشته باشد.** `opencode run --model` شکل
  `provider/model` را می‌خواهد، پس `default_model` برابر
  `9router/claude-sonnet-4-6` است. شناسهٔ بی‌پیشوند به
  `Model not found: claude-sonnet-4-6/.` می‌رسد — و برای `claude-code`
  برعکس است و شناسهٔ بی‌پیشوند می‌خواهد. به همین دلیل `_resolve_model` برای
  همهٔ هارنس‌ها پیشوند نمی‌گذارد و هر manifest مقدار خودش را می‌گوید.
- **`--format json` لازم است، نه تزئینی.** در حالت پیش‌فرض (متن)، opencode
  پیام پایانی را متن خام می‌نویسد، ولی هر دو خوانندهٔ اینجا (`_final_text` و
  `render_events`) جریان رویداد را parse می‌کنند؛ نتیجه این بود که تسکی که
  درست جواب داده بود، `answer: null` ثبت می‌شد و «چیزی تولید نکرده» به نظر
  می‌رسید.
- **نشست به `OPENCODE_PERMISSION` نیاز دارد.** بدون آن، opencode خواندن درخت
  کاری خودش را خودکار رد می‌کند؛ agent بعد از اولین فراخوانی ابزار می‌ایستد و
  run مثل یک تسک تمام‌شدهٔ بی‌کار به نظر می‌رسد.

## ۸. مشکلات رایج

### `harness2-harness: command not found`

venv فعال نیست.

```bash
source /media/kourosh/DEVNVME/projects/harness2/.venv/bin/activate
```

### `Not logged in · Please run /login` (برای claude)

نه توکن رسیده، نه دو تا اعتبار هم‌زمان داده شده. `apply claude-code` را بزن.
اگر هم `ANTHROPIC_API_KEY` و هم `ANTHROPIC_AUTH_TOKEN` ست باشد، CLI گیر می‌کند؛
adapter فقط توکن را می‌گذارد.

### claude اجرا می‌شود ولی هیچ فایلی نمی‌نویسد

حالت پیش‌فرض اجازه (`permission`) هر نوشتن را برای تأیید نگه می‌دارد و در
حالت headless کسی نیست تأیید کند — پس `exit 0` می‌دهد ولی خروجی خالی است.

manifest برای همین `--permission-mode auto` دارد. **`acceptEdits` کافی نیست**،
چون فقط ویرایش و یک فهرست کوچک از فرمان‌های «امن» را آزاد می‌کند: `echo` رد
می‌شود ولی `python3 -c`، `unzip -l`، `pandoc` و `awk` رد می‌شوند. در LAB خواندن
هر سند باینری همان `python3 scripts/read_doc.py <path>` است، پس با `acceptEdits`
عامل هیچ‌وقت نمی‌تواند کار را انجام دهد. اندازه‌گیری واقعی: یک اجرا تمام ۵۴۰۰
ثانیه‌اش را روی ۳۲۲ رد شدن گذاشت و فقط یک فایل موقت تحویل داد.

پس اگر دیدی `exit 0` است ولی `delivered` خالی، اول `permission-mode` را چک کن.
(اگر خواستی خودت عوض کنی: `auto` کلاسیفایر را در حلقه نگه می‌دارد؛
`bypassPermissions` قطعی‌تر است ولی هیچ بررسی‌ای نمی‌کند.)

### `error: unknown option '--model'` (برای dsh)

`dsh --profile headless` فلگ `--model` ندارد. مدل از پلاگین
`agent-default-model` می‌آید، پس `model_flag` خالی است و `apply` همان entry را
می‌نویسد.

### dsh با `403` رد می‌شود

دو علت جدا دارد؛ اولی را ببین، چون تقریباً همیشه همان است.

**۱. اجرای مستقیم `dsh` بدون کلید.** کلید دروازه در `.env` است و
`harness2` خودش آن را به‌عنوان `NINEROUTER_API_KEY` به هارنس می‌دهد. اگر
خودت مستقیم `dsh --profile headless ...` بزنی، از shell تو می‌خواند و آنجا
خالی است:

```bash
harness2-harness run deepseek "سلام"     # ✅ کلید تزریق می‌شود
dsh --profile headless "سلام"            # ❌ بدون کلید → 403
```

**۲. مدلی که providerش بودجه ندارد.** کلید دروازه همهٔ مدل‌ها را سرو نمی‌کند.
روی این حساب probe کردم:

| مدل | جواب دروازه | زمان |
|---|---|---|
| `claude-sonnet-4-6` | **کار می‌کند** | ~۱۲ ثانیه |
| `ag/gemini-3.8-flash-high` | **کار می‌کند** | ~۹۰ ثانیه |
| `bai/glm-5.3` | `No active credentials for provider: bai` | — |
| `Yeta/glm-5.3-flash` | `Insufficient user quota, remaining quota: $0.000000` | — |
| `apinexbond/free/glm-5.3-flash` | `Account suspended or missing` | — |

پس خانوادهٔ qwen/glm/deepseek روی این حساب بیbudget است، ولی دو مدل بالا
کار می‌کنند و هر دو در گروه dsh هستند. پیش‌فرض `claude-sonnet-4-6` است چون
هشت برابر سریع‌تر است.

**نکتهٔ مهم:** dsh مدل را از **لیست خودش** می‌خواند، نه از دروازه. اگر مدلی
کار می‌کند ولی در آن لیست نیست، خطای `has no configured model` می‌گیری، نه
۴۰۳. و `apply` آن لیست را **کامل بازنویسی** می‌کند — پس مدلی که در گروه
manifest نیست با اولین `apply` حذف می‌شود.

برای دیدن اینکه یک مدل واقعاً کار می‌کند:

```bash
curl -s -X POST http://127.0.0.1:20128/v1/chat/completions \
  -H "Authorization: Bearer $HARNESS2_9ROUTER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"ag/gemini-3.8-flash-high","messages":[{"role":"user","content":"hi"}],"max_tokens":5}'
```

### درخواست‌ها طول می‌کشند یا timeout می‌خورند

9router کند است، نه کد. کامبو `All` روی ده‌ها provider می‌گردد و بیشترشان
خطا می‌دهند. با `timeout` بلندتر امتحان کن:

```bash
harness2-harness bench pi "تسک" --run-id x/y --results-root /tmp/r --timeout 260
```

وضعیت providerها را ببین:

```bash
curl -s http://127.0.0.1:20128/api/health
```

برای سریع‌تر شدن: یا کامبوی بهتری برای مدل پیش‌فرض هارنس‌ها انتخاب کن، یا
providerهای خراب را در داشبورد 9router غیرفعال کن.

### می‌خواهم مدل را عوض کنم

`HARNESS2_SOLVER_MODEL` در `.env` را برای Harness2 عوض کن. برای خود هارنس‌ها،
`allowed_models` در manifest.

## ۹. `--substrate` کجا کار می‌کند و کجا نه

**فقط `--bench lab`** یک هارنس ثبت‌شده را می‌پذیرد:

```bash
harness2 --bench lab --substrate claude-code --k 1 --mode parallel
```

دلیلش این است که LAB لاuncher خود را با هر هارنسی که سطح `AGENTS.md` را
بخواند به اشتراک می‌گذارد. `jobbench` و `workbuddy` این کار را نمی‌کنند:
هرکدام launcher، base tree و مسیر نتیجهٔ جدا دارد، و `wb` علاوه بر آن داخل
داکر اجرا می‌شود. اگر آن‌ها را هم بپذیریم، بی‌صدا agent اشتباه اجرا می‌شود —
برای همین رد می‌کنند و پیام می‌دهند چرا.

برای JB و WB همان `oc`/`cx` را بده. برای یک اجرای تک‌تسکی با هارنس خارجی،
`harness2-harness bench` یا `do` را بزن.

**نکتهٔ claude-code:** manifest آن حالا `--permission-mode auto` و
`--output-format stream-json --verbose` دارد. اگر آن‌ها را برداری، اجرا
`exit 0` می‌دهد ولی هیچ فایلی نمی‌نویسد و trajectory خالی می‌ماند.
